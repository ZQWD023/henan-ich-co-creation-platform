## 1. 项目概述

### 1.1 一句话定位

**把散落在县域与传承人手里的非遗，变成设计师能直接使用的结构化素材 + 可执行的共创项目。**

平台不是"给非遗内容加一个聊天框"，而是用 AI 把一条完整业务链路串起来：

```
非遗知识库（结构化）→ AI 检索问答（RAG）→ AI 拆解共创任务（Agent）→ 发布为真实的共创项目 → 协作产出作品
```

### 1.2 与命题方向的对应

命题范围列出 10 个推荐方向。本作品同时覆盖其中三个的核心能力，但落点是一个**垂直场景**（非遗共创撮合）：

| 命题方向 | 本作品的实现 |
|---|---|
| 方向 2：RAG 知识问答系统 | 506 个知识片段 + BM25 检索 + 引用溯源，回答必带依据 |
| 方向 1：AI Agent 智能助手 | 5 个工具的共创 Agent：检索→查详情→查已有作品→拆任务→起草方案 |
| 方向 3：多模态 AI 创意平台 | 端侧 72 维视觉特征「以图搜非遗」；端侧纹样生成（可下载 PNG） |

补充能力：标准 **MCP 协议端点**（`/api/mcp`）、AI 安全闸门、离线优先数据层。

## 2. 需求分析

### 2.1 三类用户与真实痛点

| 角色 | 现状 | 痛点 | 对应功能 |
|---|---|---|---|
| **传承人**（供给侧） | 有意愿传播，缺渠道与方法 | 不会写方案、不会拆任务、找不到设计师；年长者数字化能力弱 | Agent 一句话生成可发布的方案；项目页只需填少量字段 |
| **设计师 / 学生**（创意侧） | 想做非遗文创，但考据成本高 | 查资料 3-5 天、纹样配色不敢乱用、怕文化表达出错 | 结构化项目资料 + 检索问答 + 取项目配色的纹样生成 |
| **公众 / 机构** | 只能"看展览" | 参与门槛高；文旅局/学校需要成体系素材 | 问答、以图搜非遗、活动报名、可检索的项目库 |

### 2.2 关键场景走查（也是演示路径）

**场景 A：一名设计师想接非遗项目**
1. 打开首页 → 首页 AI 入口（问答 / 实验室）；
2. 问"河南有哪些适合做文创的非遗？" → 得到 5 个项目 + 简要切入角度 + 检索依据；
3. 打开"钧瓷"，看工艺与看点；
4. 进 AI 实验室，输入"帮我把钧瓷做成一套文创产品" → Agent 跑 5 步 → 得到任务清单与方案；
5. 一键发布 → 项目进入"招募中"，传给传承人审核。

**场景 B：一名传承人不会写招募要求**
→ 用 Agent 生成后直接发布，只需改价格与工期。

**场景 C：评审/访客只想看看**
→ 双击 `index.html` 也能完整浏览（离线演示模式）；或访问在线演示地址。

### 2.3 需求 → 功能 → 代码映射

| 编号 | 需求 | 实现位置 |
|---|---|---|

**设计取舍**：前端零构建（原生 ES2020 + 全局命名空间）。理由：
① 评审拉下来双击即可运行，不需要 `npm i` 前端依赖；
② 同源部署时前后端一个进程，避免跨域与 CORS 配置；
③ 代价是没有 TS/打包工具 —— 我们用 ESLint + Prettier + 自建 JSDoc 约定补偿，并在文档中如实说明。

### 3.5 接口设计约定

- 统一响应体 `{ code, message, data }`，`code = 0` 表示成功；HTTP 状态码并行返回。
- 分页统一 `{ list, total, page, pageSize, totalPages }`。
- 鉴权：`Authorization: Bearer <JWT>`，7 天有效期；`optionalAuth` 用于"登录可见更多"的接口。
- 错误码分段：40000 参数 / 40100 未登录 / 40300 无权限 / 40400 不存在 / 40900 冲突 / 42900 限流 / 50000 内部 / 50200 AI。
- SSE 统一事件协议：`data: {"type":"thought|retrieval|delta|notice|done|blocked|error", ...}`，以 `data: [DONE]` 结束。

## 4. AI 技术方案（核心章节）

### 4.1 模型选型与理由

| 决策 | 选择 | 理由 | 代价/兜底 |
|---|---|---|---|
| 生成模型 | **通义千问 `qwen-plus`**（DashScope） | 中文非遗语料理解好；国内访问稳定（评审现场网络不可控）；有免费额度 | 未配置 Key / 超时 / 报错 → 自动降级到平台知识库 |
| 检索 | **自建 BM25 + 规则加权**（非向量库） | 506 片段规模小，BM25 够用且**完全可解释**（能显示命中片段与分数）；不引入 embedding 服务依赖，断网可跑 | 同义改写覆盖不足（用别名词表部分弥补，见 8.3） |
| Agent 规划 | **确定性规划器 + 真实工具调用** | 演示必须可复现；LLM 自主选工具在无 Key 时会失效 | 有 Key 时可替换为 Function Calling 循环（工具 schema 与 trace 结构已就绪） |
| 多模态 | **端侧特征（Canvas）+ 端侧生成** | 零延迟、零成本、图片不出本机（隐私）；符合赛项"鼓励浏览器端 AI 推理" | 只做"相似度检索 + 程序化生成"，不做扩散模型 |
| 协议 | **Function Calling schema + MCP JSON-RPC** | 官方考察点原文是"MCP 协议**或** Function Calling"，两者都做覆盖更稳 | — |

### 4.2 RAG：切片、检索、加权、闸门

**① 切片策略**（`rag.service.buildChunks`）

按"语义单元"切片，而非固定长度：每个项目的 `基本信息 / 项目介绍 / 历史源流 / 工艺步骤 / 技艺看点 / 传承人 / 参观信息` 各自成段，长句按标点二次切分（≤180 字）。共 **506 片**。
好处：引用时能精确到"豫剧·技艺看点"，而不是"某段文字"。

**② 中文切词**：CJK 取 **bigram**（"钧瓷窑变"→ 钧瓷/瓷窑/窑变），英文按词；索引结构为倒排表 + 文档频率。

**③ BM25 打分**（k1 = 1.5，b = 0.75）

```
idf(t)   = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(c) = Σ_t idf(t) · tf(t,c)·(k1+1) / ( tf(t,c) + k1·(1 - b + b·len(c)/avgLen) )
```

**④ 四层加权**（在 BM25 之上，按业务语义修正）

| 加权 | 系数 | 解决什么 |
|---|---|---|
| 会话上下文（当前浏览的项目） | ×1.35 | 用户从详情页跳来提问时，优先该项目 |
| 分类意图（question→分类） | ×1.8 | 问"河南有哪些戏曲"时，8 个传统戏剧项目一起进候选 |
| 项目名整体命中 | ×1.5 | "钧瓷的窑变"这类点名问句，确保该项目排第一 |
| 热门度先验（归一化后） | ×1.00–1.18 | 分类问句里"招牌项目"优先（如问武术时少林功夫靠前） |

**⑤ 实体闸门**（防"硬凑依据"）：若问题中**不含任何非遗实体**（项目名/标签/分类/口语分类词），
且最高分 < 10，则返回空结果 → 上层的 `toCitations` 给出 0 条引用 → 回答明确说明"平台知识库中没有相关内容"。
这是"AI 安全与可控性"里**不编造**的具体落点。

**⑥ 引用输出**：`toCitations(hits, {threshold: 0.35, max: 3})` → `{ id, title, section, heritageId, heritageName, score }`，前端渲染为可点击的依据 chip。

**⑦ 评测结果**（自建 **105 题**评测集，`backend/scripts/eval-rag.js` 可复现）

| 分组 | 题量 | Top-1 | 说明 |
|---|---|---|---|
| A 策划题（人工） | 19 | **100%** | 常见问法 + 3 道越界拒答题 |
| B 点名覆盖（生成） | 49 | **100%** | 每个项目一句，验证全部可检索 |
| C 分类意图（生成） | 9 | **100%** | "河南的某某有哪些"，验证 ×1.8 分类加权 |
| D 细节题（人工） | 16 | **100%** | 工艺 / 传承人 / 产地 |
| E 描述题（人工，**不含项目名**） | 12 | **100%** | 靠内容匹配，最能反映真实检索能力 |
| **合计** | **105** | **100%** | 越界拒答 3/3；平均 0.43 ms/题 |

> 完整逐题明细见 `backend/docs/rag-eval-report.md`。
> 评测集虽已扩到 105 题，但**由同一团队编写与标注**，仍存在"自己出题自己考"的偏差；B 组题面含项目名、偏简单，请以分组表为准，不要只看总数。

### 4.3 Agent：5 个工具与轨迹协议

**工具清单**（`GET /api/ai/tools` 返回 JSON Schema）

| # | 工具 | 入参 | 真实副作用 |
|---|---|---|---|
| 1 | `search_heritage` | `{query}` | SELECT 项目（含名称精确匹配优先） |
| 2 | `get_heritage_detail` | `{heritageId}` | 查工艺/步骤/传承人 |
| 3 | `list_related_works` | `{heritageId, limit}` | 查同题材作品（避免撞车） |
| 4 | `suggest_tasks` | `{heritageId, memberLimit}` | 按工艺步骤拆任务 + 推荐角色 |
| 5 | `draft_project_brief` | `{heritageId, angle}` | 生成标题/描述/招募要求 |

**编排**（`agent.service.run`）：先 `parseGoal` 解析目标（项目名/关键词/创作角度），
再把角度判定为「文创产品 / 内容传播 / 线下体验」，据此走 5 步工具链，每步产出：

```js
{ index, thought, tool, toolTitle, args, observation, durationMs }
```

**为什么是确定性规划**：现场演示不允许"这次跑出 4 步、下次跑出 7 步"。
轨迹结构已与 Function Calling 完全对齐，配置 Key 后把 `parseGoal+plan` 换成"模型选工具 → 执行 → 回填结果"的循环即可，前端与接口无需改动。

**评测**：5 个目标（钧瓷/汴绣/豫剧/少林功夫/唐三彩）→ 5/5 正确识别项目，且都产出含标题、描述、任务清单的完整方案。

### 4.4 MCP：把工具暴露成标准协议

`POST /api/mcp`（JSON-RPC 2.0）实现 4 个方法：

| 方法 | 作用 |
|---|---|
| `initialize` | 握手，返回 `serverInfo` 与 `capabilities.tools` |
| `tools/list` | 返回 5 个工具的 `name/title/description/inputSchema` |
| `tools/call` | 执行工具，返回 MCP `content` 数组（text 块） |
| `ping` | 连通性 |

`GET /api/mcp` 返回端点自述（便于发现）。这样任何支持远程 MCP 的客户端都能直接接入本平台的非遗知识库，而不必照抄我们的前端。

### 4.5 多模态（端侧）

**① 以图搜非遗**（`vision-search.js`）
Canvas 缩到 32×32 → 提取 **72 维**特征：

| 分量 | 维度 | 含义 |
|---|---|---|
| 4×4 网格平均 RGB | 48 | 主色与配色分布 |
| 4×4 网格边缘能量（Sobel 近似） | 16 | 纹理/结构密度 |
| 8 桶亮度直方图 | 8 | 明暗对比 |

L2 归一化后用**归一化欧氏距离**：`sim = clamp(1 - d / 1.15)`，取 top-k。
（早期版本用余弦相似度，结果全部落在 92–100% 无法区分，改为距离后区分度正常。）

**② 纹样生成**（`pattern-generator.js`）
取目标项目的渐变主色 + 鎏金/宣纸/墨色组成色板，用 `mulberry32(hash(heritageId+style+seed))` 驱动确定性随机，
绘制三种传统构图：

| 构图 | 算法要点 | 真实应用 |
|---|---|---|
| 四方连续 | 网格母题 + 菱形骨架 + 斜纹底 | 织物、包装底纹 |
| 团花 | 3 层放射极坐标阵列 + 四角折枝 | 陶瓷、刺绣主纹样 |
| 折枝 | 二次贝塞尔枝干 + 沿枝生叶生花 + 印章 | 年画、书签边角 |

同一种子必得同一张图（可复现、可迭代）；导出 PNG 可直接给设计同学做底纹。

### 4.6 AI 安全与可控性

| 层 | 措施 | 位置 |
|---|---|---|
| 输入 | 提示词注入（中英文）、越界话题、隐私信息、超长（>500 字）四类拦截 | `guard.service.inspectInput` |
| 检索 | 实体闸门，无实体不硬凑依据 | `rag.service.retrieve` |
| 生成 | Prompt 约束"只依据上下文回答，不确定就说不确定" | `ai.service.buildPrompt` |
| 输出 | 敏感词替换、长度裁剪（≤1200 字）、统一附 AI 标识 | `guard.service.sanitizeOutput` + `AI_NOTICE` |
| 降级 | 无 Key / 超时（15s）/ 报错 → 本地知识库回答，前端标注来源 | `ai.service.chatStream` |
| 频控 | 全局 300 次/15min，`/api/auth` 60 次/15min（可用性校验不计数） | `server.js` |
| 标识 | 每条 AI 回答底部："本回答由 AI 结合平台知识库生成，仅供参考" | 前端固定渲染 |

**降级矩阵**（现场演示不断链的关键）

| 故障 | 行为 |
|---|---|
| 无 `QWEN_API_KEY` | 走本地知识库，标注"平台知识库 / 本地" |
| 大模型超时 15s | 中止流式，改用本地知识库 |
| 后端未启动 | 前端切离线演示模式（内置示例数据 + 页面知识库问答） |
| 断网 | 同上；SSE 断开时保留已渲染内容并提示 |

### 4.7 Prompt 设计（稳定性手段）

- **角色**：河南非遗领域的资料整理员，不是闲聊助手。
- **硬约束**：只允许使用给定"资料片段"；不足以回答时明确说缺什么，不得编造人名、年代、数字。
- **结构**：先给结论（1 句），再分点（≤4 点），最后给"可继续追问的方向"。
- **长度**：≤600 字（流式逐字输出，过长影响观感）。
- **引用**：不要求模型复述引用，引用由后端 `toCitations` 单独下发 —— 避免模型"编造引用编号"。

## 5. 核心功能实现

### 5.1 流式问答链路（SSE）

```
用户提问
  │
  ├─▶ POST /api/ai/chat/stream  {question, heritageId?}
  │      │
  │      ├─ guard.inspectInput ──拦截──▶ event: blocked（前端提示原因）
  │      ├─ rag.retrieve（BM25+加权+闸门）──▶ event: retrieval（命中片段与分数）
  │      ├─ Prompt 组装（上下文 + 约束）
  │      └─ 有 Key：streamQwen ──逐块──▶ event: delta
  │         无 Key/超时：本地知识库一次性回答 ──▶ event: notice(来源) + delta
  │      └─ event: done {citations, source, elapsed}
  │
  └─▶ 前端 ai-client.js：ReadableStream 逐块解析 → 打字机渲染 → 引用 chip → AI 标识
```

要点：用 `fetch + ReadableStream` 而不是 `EventSource`，因为需要 POST body；
解析按 `\n\n` 分帧、按 `data: ` 取载荷、`[DONE]` 终止；断流保留已渲染文本。

### 5.2 Agent → 一键发布

1. `POST /api/ai/agent/stream` 推送 5 步轨迹（thought/tool/args/observation/durationMs）；
2. 最后一帧给出 `proposal{title, description, recruitNeed}` 与 `tasks[]`；
3. 前端"发布为共创项目"按钮 → 取当前登录 token → `POST /api/projects`（含 heritageId、tasks、angle）；
4. 成功后跳到项目详情页，状态 `recruiting`，其他用户可见可申请。

**闭环价值**：AI 的产出不是一段文字，而是数据库里一条可被他人申请加入的真实项目。

### 5.3 共创协作

- 申请加入 → owner 审核（通过/驳回）→ 分配任务 → 提交成果 → 结项评审 → 公示。
- 每个状态变更有权限校验（owner / member / admin）与通知写入（`notification`）。
- 详情页分 tab：概览 / 任务 / 成员 / 讨论 / 版本，按角色显示不同操作。

### 5.4 离线优先数据层

`offline-store.js` 的设计目标：**任何页面在"后端没起"时都不白屏**。

```js
// 探活一次（1.2s 超时），不通则整站进入离线模式
probeePromise: fetch('/health', {signal: AbortSignal.timeout(1200)})
apiState: 'up' | 'down'
OfflineStore.call(apiFn, fallbackFn)  // up → 真实接口；down → 内置示例数据
```

- 离线登录：演示账号 `admin/creator/designer/writer/user`（密码 123456）；
- 页面顶部只有一个小标识「离线演示」，不弹横幅、不打断浏览；
- 后端起来后 4 秒轮询发现 → 自动刷新为真实数据。

## 7. 总结与展望

### 7.1 做到什么

1. 一条**完整闭环**：知识库 → 检索问答 → Agent 拆解 → 真实项目 → 协作产出；
2. **可解释的 AI**：检索有分数、引用可点、轨迹可查、来源可辨；
3. **可兜底的 AI**：无 Key/断网/后端未启动都不白屏，AI 输出有拦截与标识；
4. **可验证的工程**：26 个单测、24 题检索评测、20 页冒烟、ESLint 0 告警。

### 7.2 不足（如实）

| 不足 | 影响 | 改进方向 |
|---|---|---|
| 前端为原生 JS，未使用 TypeScript / 现代框架 | 对应"前端代码质量 4%"的 TS 要求 | 迁移到 Vite + TS 或 Next.js（组件与状态管理可复用现有模块划分） |
| Agent 规划为确定性规则，非 LLM 自主决策 | "自主决策"表述弱 | 配 Key 后接 Function Calling 循环（schema 与 trace 已就绪） |
| 检索为 BM25，无语义向量 | 同义改写覆盖不足 | 引入 bge-small 端侧 embedding（Transformers.js）做混合检索 |
| 纹样为程序化生成，非扩散模型 | 与"图像生成"预期有差距 | 有额度时接图像 API，UI 与流程不变 |
| 评测集 105 题，但标注来自同一团队 | 存在自评偏差 | 找第三方双人标注、加入对抗性问法 |

### 7.3 展望

- **端侧深化**：Transformers.js 做端侧语义检索、WebGPU 加速纹样渲染，让平台在县域文化馆的低配设备上也能跑；
- **MCP 生态**：把"非遗知识库"作为 MCP Server 开放，让第三方 Agent 直接调用；
- **商业闭环**：撮合服务 → 作品授权分成 → 机构 SaaS（详见《商业计划与价值主张》）。

## 8. 附录

### 8.1 创新点（技术与应用）

**技术创新**
1. **分类意图加权 + 实体闸门**的 BM25 变体：既能在"有哪些戏曲"这类问句上做同分类扩散，又能在越界问句上拒答；

4. **端侧多模态双能力**：72 维特征检索 + 项目配色驱动的程序化纹样生成，全程不上传图片；
5. **双协议工具集成**：Function Calling schema 与 MCP JSON-RPC 端点并存。

**应用创新**
1. 把"非遗资料库"变成"共创项目生产线"，AI 负责翻译（把工艺翻译成任务）；
2. 面向传承人的**低门槛发布**：一句话 → 方案 → 发布，解决"会做不会写"；
3. **离线优先**适配县域网络条件，断网仍可演示与浏览。

## 12. 附录 E：部署步骤（Render，约 10 分钟）

1. 把仓库推到 GitHub（Public 或给评审访问权限）；
2. Render → New → **Blueprint** → 选择本仓库（会自动读取 `deploy/render.yaml`）；
3. 在 Environment 里填 `JWT_SECRET`（32 位以上随机串）与可选 `QWEN_API_KEY`；
4. 部署完成后访问 `https://<name>.onrender.com/`，`/health` 应返回 `{"status":"ok"}`；
5. 免费实例 15 分钟无访问会休眠：用一个免费探活（每 10 分钟）保持唤醒；
6. 用只读评审账号验证：登录 → 共创广场 → AI 问答 → AI 实验室 → Agent 一键发布（**不要真的发布**，避免改数据）。

  proxy_buffering off;      # 关键
