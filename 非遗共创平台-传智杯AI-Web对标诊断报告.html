01

先说清楚：你手里到底是什么

在谈改进之前，先把项目拆开看。很多"改进建议"之所以落不了地，是因为没分清哪些是已经做好的、哪些是根本没做的。

项目画像

维度实际情况
主题定位河南省非物质文化遗产「共创平台」——传承人、设计师、公众三方共创，正好落在赛道的 「文化共创」 主题方向内
技术形态纯静态站点：原生 HTML + CSS + 原生 JavaScript，无前端框架、无后端、无数据库、无构建工具
数据与"后端"数据硬编码在 data.js；用浏览器 localStorage 冒充数据库，存储用户、作品、报名、收藏
外部依赖Font Awesome（图标 CDN）、维基百科 API / 维基共享资源（图片）、LoremFlickr（关键词图）、阿里云 DataV GeoJSON（河南地图边界）
代码规模约 4150 行（JS ≈ 2200 行、CSS 1001 行、HTML ≈ 950 行），14 个页面 / 13 个 JS 模块
命名遗留压缩包叫「算法网站」，但内容是非遗平台；目录里仍留着 algorithms.js / algorithm-detail.html 等旧"算法网站"改造残留文件

已经做好的部分（这些别动，是加分底盘）

  • 数据访问层设计规范。 把数据封装成 ICH 对象统一暴露 getProject / searchProjects / getFeaturedProjects / getStats，职责清晰，比把数据散在页面里强很多。
  • 一条完整的功能闭环。 注册登录 → 浏览/搜索/筛选项目 → 收藏 → 投稿共创 → 点赞 → 报名活动 → 解锁成就，用户旅程是通的，不是只有首页的门面工程。
  • 真做了 GIS 可视化。 拉取阿里云 DataV 河南省 GeoJSON，自己实现等距柱状投影把经纬度映射成 SVG，城市光点可悬停出项目提示、可点击跳转。这是全项目技术含量最高的一处，评委容易记住。
  • 有一套成体系的设计语言。 CSS 变量定义了朱砂红/鎏金/宣纸/青玉配色，4 个响应式断点，卡片阴影、过渡动画统一，视觉是有辨识度的"中式文化"风，而不是默认 Bootstrap 味。
  • 有工程健壮性意识。 图片做了"维基共享资源精确图 → 图片失败回退到维基 API → 再失败就移除走渐变兜底"的三级降级；搜索框、空状态、Toast、确认弹窗都写了。
  • 有游戏化设计。 8 个成就勋章 + 完成度百分比，能提升用户激励与留存，这在同类作品里算差异化细节。
一句话结论

这是一个"设计用心、工程扎实、但没有技术纵深"的作品。它的短板不是做得不细，而是技术路线选错了方向——它把所有力气都花在了"把静态页面做漂亮"上，而这恰恰是评分权重最低、且人人都会的部分。

04

差距诊断：按"扣分严重度"排序

每一条都标注了它挂在哪几个评分维度上。P0 决定你能不能进国赛，P1 决定能不能拿奖，P2 决定能不能拿高奖。

P0 致命
全站没有任何 AI 能力，与"AI Web"赛道命题完全错位
影响维度：创意与原创性、技术实现、赛道命中

赛道名称是「AI Web 网页开发挑战赛」，规则明确要求作品"融合 AI 技术"，并要"体现 AI 技术如何助力实际问题的解决与体验优化"。而当前项目的所有逻辑都是纯前端静态渲染：搜索用的是 String.includes() 的字符串匹配，推荐用的是按 popularity 字段降序排，没有任何模型调用、没有智能推荐、没有语义理解、没有内容生成。

为什么致命：这不是"少了一个亮点"，而是答错了题。评委打开项目找不到 AI，第一印象就归类为"普通静态展示站"，后面再漂亮也很难救回来。

怎么改 见第 6 节的 8 个 AI 功能设计，至少落地 3 个（推荐：AI 非遗问答 + AI 文创生成 + 智能语义搜索），且 AI 必须嵌入业务流程而非孤立聊天框。

P0 致命
没有使用前端框架（Vue / React），未满足技术能力要求
影响维度：技术实现（25%）、技术栈架构

官方技术能力第②条写的是"深入掌握前端主流框架 Vue 或 React"，国奖/省奖作品普遍是 Vue.js 或 React + Node.js 的现代技术栈。当前项目是原生多页应用（MPA），每个页面重复引入 data.js + script.js，靠 innerHTML 拼接字符串渲染，没有组件化、没有状态管理、没有路由。

为什么致命：25% 权重的"技术实现"维度里，"技术应用高效、代码规范"是拿分关键。原生 innerHTML 拼串在评委眼里属于"能跑但不够专业"，直接压在"一般"档，25% 的分几乎全丢。

怎么改 用 Vue 3 + Vite（学习曲线比 React 平缓，且国内教学资源多）重构：把页面拆成组件（ProjectCard、WorkCard、NavBar…），用 Pinia 管登录态，用 Vue Router 管路由，把 data.js 抽成 store 或 API 层。

P0 致命
没有后端与数据库，用 localStorage 冒充，且密码明文存储
影响维度：技术实现（25%）、上线运营能力（20%）、安全隐患

所有"数据"都存在用户浏览器的 localStorage 里：注册的用户存在 henanICHUsers，登录态存在 henanICHCurrentUser，作品、报名、收藏同理。这意味着换一台设备、换一个浏览器，数据全部消失；所谓"平台"实际上只是"本机演示"。

更严重的是安全隐患：注册时 password 被原样明文写进 localStorage（见 auth.js），登录时用 u.password === password 直接比对。而官方"技术实现"维度里明确写着："存在重大错误或安全隐患"直接掉到最差档（0–4 分）。这一条足以单独扣掉几分。

怎么改 加一个后端（Node.js + Express 或 Python + FastAPI），数据库用 MySQL / PostgreSQL / SQLite；密码必须 bcrypt 加盐哈希存储，用 JWT / Session 管理登录态。这是硬性补齐项，没有它"上线运营"20% 也拿不到。

P1 重要
内容可信度存疑：图片与关键词不匹配、传承人信息为"示范性展示"
影响维度：商业价值与可行性、创意与原创性、作品严谨性

这是很多团队忽略、但评委一问就露馅的地方：

① 图片与内容不相关。 项目对大多数非遗用的是 LoremFlickr 按英文关键词随机取图（如 "chinese,opera,stage"），返回的是与具体非遗无关的随机照片。豫剧卡片底下可能挂着一张欧美歌剧照——这在答辩现场是灾难。

② 数据来源没交代。 只有 6 个项目配了维基共享资源的精确照片，其余靠关键词兜底；顶部却没有任何"数据来源"标注或引用。

③ 传承人信息风险。 data.js 自己注明"传承人信息为示范性展示"，但页面上用的是真实姓名、头衔与生平描述。这类"未经授权使用真人信息、内容可能不准确"的做法，既可能踩到知识产权/名誉权红线，也会被评委质疑"数据是编的"。

怎么改 一律换成可溯源的官方图源（文旅部门官方图库、自有拍摄、明确授权的素材）；每条项目标注来源链接；真实人物信息要么取官方公示内容并注明出处，要么匿名化/化名处理。

P1 重要
完全没有"上线运营"证据，20% 权重基本放弃
影响维度：上线运营能力（20%）

"上线运营能力"占 20%，要求"项目以上线运营，包括市场推广策略、运维计划、用户反馈机制"。当前项目：没有部署（还是本地 zip）、没有域名、没有可访问的线上地址、没有推广方案、没有运维/反馈设计。

怎么改 三步走：① 真的把它部署上线（Vercel / 阿里云 ECS / 腾讯云轻量服务器，挂个域名）；② 在提交文档里写运营方案（种子用户从哪来、内容怎么更新、和文旅局/学校非遗社团怎么合作、数据怎么埋点回收）；③ 做出至少一轮真实用户数据（哪怕 50 个种子用户、200 次浏览，截图放进 PPT，含金量远高于空谈）。

P1 重要
缺"商业模式 + 市场分析"文档，商业价值维度拿不到分
影响维度：商业价值与可行性（20%）

官方标准是"清晰的商业模式、明确的市场定位、详尽的市场分析"。项目有"非遗共创"这个概念，但没有任何落地为生意的说明：谁来买单？文创作品如何变现？和传承人怎么分账？平台抽佣还是内容付费？目标用户画像是什么？市场有多大？

怎么改 补一份 3–5 页的商业计划：目标用户（院校师生/文创消费者/文旅单位）、价值主张、变现路径（共创作品打样分成 / 文创电商抽佣 / 非遗研学课程 / 政企数字化服务）、竞品对比、SOM/TAM 粗估。

P2 加分
搜索与推荐的"智能度"低，是无 AI 的直接症状
影响维度：创意与原创性、用户体验

搜索是 includes() 子串匹配，搜"戏曲"匹配不到"豫剧"（除非标签里有），没有同义词/拼音/纠错/语义能力；"精选项目"是按 popularity 字段硬排；"相关共创作品"是按 projectId 精确相等过滤。这些都不是"个性化"或"智能"。

怎么改 用向量语义检索替代子串匹配（user query → embedding → 与项目向量算余弦相似度），即可实现"搜'唱戏的'也能找到豫剧、曲剧"。这是补齐 AI 最省力的切入口。

P2 加分
工程化与质量保障缺失：无构建、无测试、无 SEO、无无障碍
影响维度：技术实现、用户体验

① 无构建工具（无 Webpack/Vite）——源码不做压缩、不做资源指纹、直接裸发；② 无任何测试（无单元/端到端），而官方技术能力第⑥条明确要求"测试与上线流程"；③ SEO 弱——内容全靠 JS 运行时渲染，爬虫抓不到正文，也没有 sitemap/结构化数据；④ 无障碍缺失——图标按钮、地图光点、轮播控件普遍没有 aria-label，键盘与读屏用户不可用。

怎么改 迁移到 Vite（自带构建与压缩）；补 Vitest/Playwright 冒烟测试；用 SSG/SSR（如 Nuxt）或至少给关键页做预渲染；给交互元素补 ARIA 属性。

P2 加分
"算法网站"改造痕迹未清理，叙事不统一
影响维度：创意与原创性、作品完整性

压缩包与目录名仍叫「算法网站」，工程里保留着 algorithms.js（内容只有一句"已被 projects.js 取代"）、algorithm-detail.html（一个 0 秒跳转的空壳）。评委若翻源码看到这些，会立刻意识到这是"别的项目改的"，损害原创性印象。

怎么改 彻底删除无用残留文件、统一命名、重写 README 与技术方案，让整个项目的"故事"从头到尾自洽。

05

精进路线图：按优先级分三阶段

不要一上来就全部推倒重来。按下面的顺序做，每一阶段结束都是一个"能提交、能答辩"的完整版本（省赛→国赛恰好是三级赛制，天然对应三轮迭代）。

P0 · 先救命
把赛道命题补上
目标：从"静态站"变成"AI Web 应用"
  • 接入大模型 API（通义/DeepSeek/智谱），落地 AI 非遗问答（RAG 检索项目库作答）

06

「文化共创」主题下，可以做什么 AI 功能

这是全报告最该抄走的部分。一个好原则是：AI 要长在业务流程里，而不是首页挂一个聊天框。下面 8 个功能都能复用到这个非遗项目上，★ 标记的是最推荐优先做的。

1AI 非遗知识问答（RAG）★
把 33 条项目数据、传承人、历史渊源做成知识库，用户问"钧瓷的窑变是怎么回事""河南有哪些戏曲"时，模型基于知识库作答并给出处。
实现：数据向量化 → 向量库（Chroma/Milvus）→ 检索 + 大模型生成。可复用现有 ICH 数据层。
2AI 文创设计生成（文生图）★
用户选一个非遗（如"汴绣"）+ 一个风格（如"国潮"），AI 生成该元素的文创图案/纹样/周边效果图——直接服务"共创"这个核心概念。
实现：文生图 API（通义万相 / 即梦等），把非遗关键词 + 风格词拼成 prompt，生成结果回流到共创广场。
3智能语义搜索 ★
把前端的 includes() 换成向量语义检索："唱戏的""会响的泥玩具""青色的瓷器"都能命中豫剧、泥咕咕、汝瓷。
实现：项目描述预先 embedding 入库，查询时算余弦相似度排序；成本低、见效快。
4AI 个性化推荐
基于用户收藏/浏览/点赞行为，推荐"你可能感兴趣的非遗"。替代现在的按热度硬排。
实现：起步用内容相似度（用户的收藏项目向量做质心），进阶用协同过滤。
5AI 共创助手
投稿时用户只写一句模糊创意，AI 帮它扩写成完整的产品定位、目标人群、设计说明、标签——降低投稿门槛，提高作品质量。
实现：表单内嵌大模型改写；可顺带自动生成标签与分类。
6AI 语音讲解 / 口述史整理
把非遗简介转成音频讲解（TTS + 数字人），或把传承人口述的录音做 ASR + 摘要，沉淀成结构化内容。契合"非遗影像库/口述史"的真实需求。
实现：ASR（语音识别）+ LLM 摘要 + TTS 合成；可对接"数字化赋能非遗"政策叙事。
7非遗知识图谱可视化
把"项目—传承人—地区—技艺—关联作品"做成可交互的知识图谱，点一个节点带出一片关系网。和你已有的地图可视化形成组合拳。
实现：用 ECharts Graph / Cytoscape.js 渲染；关系由 LLM 从文本抽取。
8AI 多模态识别（拍照识非遗）
用户上传一张瓷器/脸谱/年画照片，AI 识别出对应的非遗门类并跳转到详情页。移动端体验极佳，适合放进演示视频。
实现：多模态视觉模型（VLM）分类 + 相似检索；作为"炫技"亮点。
最小可行组合（建议照这个抄）

先做 ① AI 问答 + ③ 语义搜索 + ② 文生图共创 这三个。它们共同的特点是：复用你已有的非遗数据、强绑定「文化共创」主题、且能在 3 分钟演示视频里形成"输入—AI 处理—输出"的完整闭环。这正是国奖评语里"智能交互设计 + AIGC 内容生成深度融合"的直接对应。
